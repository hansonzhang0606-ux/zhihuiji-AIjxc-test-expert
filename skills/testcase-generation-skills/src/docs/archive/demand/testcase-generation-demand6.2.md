### 核心原则（评审定稿）

1. **全文归档 ≠ 全文注入**：知识可迁入知识库供人审；生成侧只注入 Script 截取后的结构化切片。  
2. **一套拓扑真源**：页面跳转只以 `页面关系.md` 为准。  
3. **按端切片**：同文件可对照多端（利人审）；机器读取必须按端节切分，每条事实带适用端。  
4. **宁缺毋滥**：只收核心功能 / 易被影响 / 端差异大；禁止元素百科。  
5. **人审中文路径；机器另有索引**：人工看中文树；Script 用生成的只读索引定位。  
6. **页面可直达、元素可追接口**：Web 页面记录可跳转的前端 URL 模板；Web/App 核心元素记录实际调用的后端接口。  
7. **技术引用不绕过 C-TP**：KB 的 URL/API 先进入测试点 `technical_refs`，Stage4 再复制到用例；Stage4 仍禁止直接读取 KB。

## 一、目标与非目标

### 1.1 目标

1. 为星火提供可人审、可截取的长期知识（模块支持、页面关系、Web 页面 URL、精简元素、分端后端接口、补充口径）  
2. Stage 生成前按 C-CTX / C-MOD **三级召回**，写入 `domain_facts.json`  
3. `project_context.md` **全文迁入**知识库；Stage 不再以 stage 模板为权威  
4. 「补充知识库」旁路入库；默认不自动晋升人审临时口径  

### 1.2 非目标

- 上线前铺满所有模块 / 全站元素  
- Agent 无截取通读 `templates/知识库/`  
- 把 README、Demand 正文、矩阵「说明」节默认灌进 1A/3A Prompt  
- 在页面文件重复整张模块支持矩阵  
- 文件名使用 `kb` / `M0` / `M1` 等代号（例外：库根 `README.md`）  

### 1.3 入库准入

至少满足其一：**核心功能** | **易被影响** | **端差异大**。

| 禁止入库 | 例 |
|----------|----|
| 壳层全量 | Header / 侧栏全菜单 / 页签罗列 |
| 稳定配置 | 普通属性字段、无端差开关选项 |
| 采集噪声 | 坐标、DOM class、视口尺寸 |
| 探索原稿未裁剪 | `智慧记AI进销存元素探索/*` 直接入库 |

### 3.1 目录树

```text
src/templates/知识库/
├── README.md                         ← 库纪律（英文名；不注入业务 Prompt）
├── 知识库索引.json                   ← Script 生成的只读索引（人勿手改）
├── 模块矩阵总览.md                   ← 上：模块分层；下：支持矩阵；说明区最后
├── 销售/
│   └── 销售/
│       ├── 页面关系.md               ← 拓扑唯一真源
│       ├── 主页面_销售单列表页.md
│       └── 子页面_销售单开单页.md      ← 按需创建
└── 小程序/
    ├── 云店/
    │   ├── 页面关系.md
    │   └── 主页面_….md
    └── 订货分析/
        └── …
```

### 3.2 命名规则

| 规则 | 约定 |
|------|------|
| 根目录 | `知识库`（中文）；运行时根 = `kb_root`（§7.3） |
| 业务路径 | 全部中文；与「模块分层」一级/二级名一致 |
| 例外英文名 | 仅 `README.md`；`知识库索引.json` 为本地生成物 |
| 禁止 | `kb`、`M0`、`elements`、`rules` 等作主文件名；废弃路径 `templates/kb/` |
| 页面关系 | 每二级模块固定 `页面关系.md` |
| 主页面 | `主页面_{统一页面名称}.md`（通常 1 个） |
| 子页面 | `子页面_{统一页面名称}.md`（**仅当有元素或补充说明时创建**） |
| 统一页面名称 | 文件头 `页面标识` 与关系表共用（如 `销售单列表页`，须语义唯一且带「页」） |

### 3.3 小程序独立域

- `知识库/小程序/云店/`、`知识库/小程序/订货分析/` 为**独立产品面**。  
- **禁止**把 Web「云店」二级模块目录下的页面知识拷贝冒充小程序。  
- 电脑端 / APP 同构模块：写在同一 `{一级}/{二级}/` 树内，用端分节对照。

### 3.4 根 README（规则唯一维护处）

`知识库/README.md` 只供维护者与 Script 使用，默认不注入业务 Prompt。至少声明：

- 四类文件的唯一职责；
- 最小读取顺序：`索引 → 矩阵机器区 → 页面关系对应端 → 命中核心元素 + 被引用补充`；
- 端标识统一为 `web` / `app`（标题可用「电脑端（Web）」/「APP端」）；
- 页面清单「支持端」是页面端支持唯一表达；
- Web 本端页面对照表同时维护可跳转的「前端 URL 模板」；禁止保存登录态、Token 或真实租户参数；
- 每条新增/更新核心元素必须给出本端「后端接口」，或明确 `无后端调用（纯前端）` / `待确认`；
- 无核心元素不建空端节；无核心元素或补充说明不建页面文件；
- 通用模板纪律只写 README，禁止复制进每个业务文件。

## 四、模块矩阵总览

### 4.1 迁移范围与职责拆分

| 原 skills 模板 | 迁入知识库 | 仍留在用例生成 skills |
|----------------|------------|------------------------|
| `module_mapping.md` 一级/二级分级 | **【机器区】模块分层**（仅中文名两列） | 关键词匹配、跨模块链路、自动匹配规则 |
| `project_context.md` 各端/版本支持 | **【机器区】模块支持矩阵**（及后续分端表） | — |
| `project_context.md` 产品/端/版本说明 | **【说明区】**（默认不注入） | — |

迁完后：

- Stage / 3B / 入库校验的**模块名权威** = 知识库「模块分层」  
- 需求→模块**如何匹配** = skills 内规则（可继续读精简后的 `module_mapping.md` 匹配节，或独立匹配文件）  
- 旧 `project_context.md` 保留跳转或废弃说明，禁止继续扩写业务矩阵  

### 4.2 文内结构（上分层，下支持）

```text
# 模块矩阵总览

## 【机器区】模块分层          ← 一级 | 二级（一行一级；二级用「、」并列）
## 【机器区】模块支持矩阵      ← 一级 | 二级 | web | app | 小程序 | 产品版本
## 【机器区】电脑端 · 功能支持矩阵   ← 正式迁移后可按端拆表
## 【机器区】APP端 · 模块迁移矩阵
## 【机器区】小程序 · 独立域矩阵

## 【说明区】产品 / 端 / 订阅版本 / …
```

**模块分层纪律：**

- 只写两列：`一级模块 | 二级模块`；二级多个时用顿号并列，如 `| 商品 | 商品、规格管理、单位管理 |`
- **禁止**写入匹配规则、英文标识、关联对象、测试场景
- 一级名与目录 `{一级}/` 一致（若历史 mapping 写作「销售模块」，知识库用短名 **销售**）
- 未出现在「模块支持矩阵」中的分层二级，端支持默认 **未知**（不自动裁掉，记 warning）
样例阶段支持矩阵可只填已入库模块：

```markdown
| 一级模块 | 二级模块 | web | app | 小程序 | 产品版本 |
|----------|----------|-----|-----|--------|----------|
| 销售 | 销售 | 支持 | 支持 | 不支持 | 未知 |
```

| 区 | 人审 | Script / Prompt |
|----|------|------------------|
| **机器区 · 分层** | 先看 | 校验二级模块名；建目录合法性 |
| **机器区 · 支持** | 先看 | 3B / 端裁剪；最终支持 = 版本 ∩ 端 |
| **说明区** | 后看 | **默认不注入** |

> **硬规则：** 全文迁入是归档；**禁止**把说明区整段塞进 1A/3A；**禁止**把匹配规则写进知识库。

### 4.3 多矩阵冲突规则（P0）

单元格取值：`支持` | `不支持` | `部分支持` | `未知`。

```text
最终是否生成该端标签 / 是否召回该模块页面知识：

  最终支持 = 产品版本支持 ∩ 端支持

其中：
  - 电脑端：看「电脑端 · 功能支持矩阵」对应 L2 ×（开单/单店/多店/国际…）
  - APP端：看「APP端 · 模块迁移矩阵」；未迁移 = 不支持（不得用电脑端表默认拷贝）
  - 小程序：只看「小程序 · 独立域矩阵」；与主站 L2 表无交集假设
  - 任一维为「不支持」→ 最终不支持
  - 出现「未知」→ 不自动裁掉，但截取报告记 warning；人审①/矩阵维护须消未知
  - 「部分支持」→ 允许召回，statement 须带限制短注
```

优先级：端矩阵否决电脑端“有模块”的假设；小程序域与主站模块树互不继承。

## 五、页面关系（拓扑唯一真源）

### 5.1 设计目标

解决三类实际问题：① 各端实现页面多少不同；② 同一功能各端产品命名不同；③ Web 用例需要直接打开目标页面。  
做法：**跨端统一页面名称**（语义唯一） + **分端写跳转路径与本端叫法** + **Web 前端 URL 模板**；元素差异和后端接口不进本文件。

### 5.2 推荐结构

```text
# 页面关系 · {一级} / {二级}

## 1. 页面清单（跨端统一页面名称）
| 统一页面名称 | 角色 | 支持端 | 一句话说明 |
| 销售单列表页 | 主页面 | web+app | 查询与进入开单/查看的入口 |
| 销售单开单页 | 核心子页面 | web+app | 新增/修改/复制共用 |
…（元素文件路径只在索引维护；跨模块目标页可另表）

## 2. 电脑端（Web）
### 2.1 本端页面名与 URL（对照）
| 统一页面名称 | 本端页面名 | 前端 URL 模板 |
| 销售单列表页 | 销售单列表页 | `/sales/order/list` |
| 销售单详情页 | 查看销售单页 | `/sales/order/{order_id}` |

### 2.2 跳转路径               ← 起点 | 动作 | 终点（只用统一页面名称）

## 3. APP端
### 3.1 本端页面名（对照，不含 Web URL）
### 3.2 跳转路径
```

| 字段 | 约定 |
|------|------|
| **统一页面名称** | 跨端唯一、**语义唯一**的页面名，**须带「页」后缀**（如 `销售单列表页`，禁止仅用「列表」）；文件名 `主页面_{名称}.md` / `子页面_{名称}.md`；**禁止**「标识+别名」双轨 |
| **角色** | `主页面` \| `核心子页面` \| `子页面` |
| **支持端** | 固定为 `web` \| `app` \| `web+app`；禁止写中文枚举或 `PC端/APP端` |
| **一句话说明** | 业务职责；不写控件细节 |
| **跳转路径** | 分端维护；列为 `起点 \| 动作 \| 终点`；新增/修改/复制是**动作**，不是多个页面名称 |
| **本端页面名** | 仅对照表；供人读产品名，机器路径表仍用统一页面名称 |
| **前端 URL 模板** | 主要用于 Web；允许绝对 URL 或以 `/` 开头的路由模板；动态段统一写 `{参数名}`；一个页面可用 `<br>` 列多个稳定入口 |

#### 5.2.1 前端 URL 纪律

- Web 支持页应补充 URL；新建/更新且状态拟为 `已确认` 的 Web 页面不得留空。历史页迁移期缺失只报 warning，不得猜测。  
- 优先保存**稳定路由模板**，如 `/sales/order/{order_id}`；若保存绝对 URL，必须是可共享环境地址，禁止个人 localhost。  
- 路由模板由运行环境的 `WEB_BASE_URL` 组合为可点击地址；绝对 URL 可直接跳转。  
- 禁止保存 Cookie、Token、签名、真实 tenant/user/order 值；query 参数仅保留必要键并使用 `{placeholder}`。  
- URL 是页面定位信息，不是页面拓扑；页面间关系仍只认「跳转路径」。  
- App 默认不要求 URL；未来若存在稳定 deeplink，应另加 `APP Deeplink` 字段，不得塞入 Web URL 列。

### 5.3 纪律

- **只在本文件维护页面清单、本端产品名、Web 前端 URL 与跳转路径**。  
- 页面清单的「支持端」是页面端支持**唯一表达**；分端章节不重复「有页/无页」表，也不列本端不存在的页面。  
- 页面关系不维护元素文件路径；路径只由 `知识库索引.json` 导航。  
- 跳转路径固定三列 `起点 | 动作 | 终点`；动作已能表达含义时不增设重复「说明」列。  
- **禁止**在本文件写表头设置、字段池、端内控件差异（→ 元素文件）。  
- 无元素可写的页：清单可有，但不建元素文件，索引 `file=null`（如仅 App 有的中间页）。  
- 元素文件**不写**跳转入口；进出关系只维护在本文件。  
- 通用模板规则只写库根 `README.md`，不复制到每个业务关系文件。  
- Web 详情下游动作很多时：**按需追加边行**，不预先穷举；未出现在 App 边表的动作默认 App 未实现。

## 六、主页面 / 子页面文件

### 6.1 文件头（P2，建议必填）

```yaml
页面标识: 销售单列表页      # 与页面关系「统一页面名称」一致（语义唯一）
页面角色: 主页面          # 主页面 | 核心子页面 | 子页面
状态: 已确认              # 草稿 | 待确认 | 已确认 | 已废弃
更新时间: 2026-07-29
来源: 人审补充
```

权威划分：

- 页面角色、支持端：以 `页面关系.md` 页面清单为准；
- 状态、更新时间、来源：以页面文件 frontmatter 为准；
- 索引字段均由 Script 生成，不形成第三套人工真源；
- `页面角色` 若保留在 frontmatter，仅为派生校验字段，必须与页面关系一致；
- LLM 业务切片默认不注入 frontmatter。

### 6.2 元素入库过滤（写入前必做）

知识库**不是**页面控件百科。候选元素须先过滤，**至少命中一条**才允许写入「核心元素」：

| 准入条件 | 含义 | 例 |
|----------|------|----|
| 核心功能 | 主路径关键能力，测不到会漏主流程 | 开单表头配置、自定义表头可填/只读展示 |
| 易被影响 | 配置/字段池/跨单联动，易写错预期 | 公用表头字段、已显示≠他单自动已显示 |
| 端差异大 | Web/App 行为实质不同 | Web 有列表表头齿轮、App 无 |

**默认不入库：** 常规静态文案、纯展示无分支、与他页完全同构且无端差的低价值控件、某端不存在的控件（禁止写「无 xxx」伪行）。  
**跳转/入口一律不写进页面文件：** 进出本页只读 `页面关系` 分端跳转路径，禁止在元素文件重复「入口」节（防双拓扑）。
**禁止空节/空文件：** 某端无核心元素则不建该端节；整页无核心元素且无补充说明则不建元素文件，索引 `file=null`。

### 6.3 正文结构

```markdown
# 主页面：销售单列表页

## 页面简介
一句话：页面功能 + 支持端（如 Web + APP）

## 电脑端

### 核心元素
| 元素 | 位置 | 输入/选项 | 交互 | 交互结果 | 后端接口 | 下游影响说明 |
|------|------|-----------|------|----------|----------|--------------|
| 表头.设置 | … | … | … | … | `GET /api/v1/columns`（查询可选列）<br>`POST /api/v1/columns/config`（保存配置） | — 或 见补充说明·{元素} |

## 补充说明
- 见补充说明·{元素}：……（下游超过 20 字时落此处）
- 某端没有但容易误写的控件：仅在此写禁写口径
```

| 列 | 用途 | 精简规则 |
|----|------|----------|
| 位置 | 控件在哪 | 一句定位 |
| 输入/选项 | 可选值、输入约束、上游来源 | 如 `可选列←公用池`；原「被影响」并入本列 |
| 交互 | 本端怎么操作 | 只写本端 |
| 交互结果 | **仅本页**立刻结果 | 不写他页/他端 |
| 后端接口 | 该元素在**本端**直接调用的 API | `METHOD /normalized/path` + 可选短用途；多接口用 `<br>`；不写 host/鉴权/真实参数 |
| 下游影响说明 | 他页/他单/他端后果 | **≤20 字**写本格；**>20 字**改写「见补充说明·{元素}」，正文放到补充说明 |

**不设「角色」列：** 能入库的已是重点，无需再标入口/易变。

**端缺控件：** 该端不写行、不建空节；确需防止误写时才在补充说明写一句禁写口径。

#### 6.3.1 后端接口纪律（Web / App 均适用）

- 同一元素在 Web、App 调用不同接口时，分别写在对应端节；禁止用 Web 接口默认代替 App。  
- REST 写法：`GET /api/v1/orders/{order_id}`；GraphQL 写法：`POST /graphql#QueryOrder`；事件/长连接可写 `WS /path#event`。  
- 每条新增/更新核心元素必须满足其一：  
  1. 一个或多个明确接口；  
  2. `无后端调用（纯前端）`；  
  3. `待确认`（此页面不得因此直接升为 `已确认`，须在人审补齐或明确接受缺口）。  
- 接口只保存 Method、规范化 Path/Operation、≤20 字用途；请求字段、响应约束或接口联动确属易错知识时，写「补充说明·{元素}.接口」，不扩成接口百科。  
- 禁止保存域名、环境 IP、Cookie、Authorization、Token、签名、真实业务 ID、完整请求/响应样本。  
- 一个页面级公共加载接口若服务多个元素，可在各元素引用同一规范接口；不要为了去重创建脱离元素的第二套接口文件。

文件命名：`主页面_{统一页面名称}.md` / `子页面_{统一页面名称}.md`。

### 6.4 同文件多端（人审友好 / 机器隔离）

- 人审：有核心知识的端在同一文件分节对照；无知识的端不占位。  
- 机器：**只提取 C-CTX `platforms.in_scope` 对应节**；输出每条事实必须带 `platforms`。  
- **禁止** Agent 为省事整页 Read 后自行“摘要多用”。

### 7.3 入库子流程（唯一流程；含可选 Git）

**知识库根 `kb_root`：**

1. 若 `kb_remote.enabled=true` 且配置了 `local_path` → `kb_root = local_path`  
2. 否则 → `kb_root = src/templates/知识库/`（技能仓默认样例/本地根）  
3. 全文禁止再写死第二套根路径；§七～§九 凡「写入/读取知识库」均指 `kb_root`

```text
    ↓

    ↓

    ↓
[Script] kb_git_push          ← 仅 enabled=true；默认直推配置 branch（见 §7.8）
    ↓

```

#### 7.7.1 URL / API 与用例的双向流转

**KB → 测试点 → 用例：**

```text
已确认 KB
  → extract_kb 产出 page_url / backend_api facts（带 kb_ref + platform）
  → Stage3A 仅把与当前页面/元素/端命中的事实写入 C-TP.technical_refs
  → Stage4 从 C-TP 原样复制到 C-TC.technical_refs
  → XMind 在用例下展示「技术引用 / 页面地址 / 后端接口」
```

- URL 可用于用例前提或首步“直接打开页面”；若为相对路由，运行时用 `WEB_BASE_URL` 组合。  
- API 默认是**技术引用**，不是业务期望；只有测试点明确验证请求、响应、调用次数或异常时，才写入步骤/期望。  
- Stage4 仍只读 C-TP，不得为拿 URL/API 直接读取 `domain_facts` 或长期 KB。  
- 同一 TP/TC 只带实际相关的引用；禁止把页面全部接口灌入每条用例。

**用例 → KB 回流：**

```text
C-TC / 最终 XMind 中的 technical_refs
  → 6.3 source adapter 读取
  → URL 按 platform+page_id 归到页面关系
  → API 按 platform+page_id+element_name 归到元素行
  → 与现有 KB 对账
  → KB-概审 / KB-内容审
  → 写回长期 KB
```

- 结构化 `technical_refs` 优先；从步骤/前提自由文本抽出的 URL/API 只能作为候选，必须人审。  
- 接口缺少元素归属时禁止挂到“页面任意元素”；进入概览待问或 `_inbox`。  
- 回流时先规范化：去域名/敏感 query/真实 ID，Method 大写，动态段改 `{placeholder}`。  
- 同一接口路径但 Method 不同视为不同接口；新旧接口冲突按 6.3 覆盖协议处理，禁止静默替换。  
- 用例里出现的第三方、测试桩、上传 CDN、埋点接口，只有满足 §1.3 准入且与产品行为直接相关时才允许回流。

### 7.8 语义库远程 Git（可配置；默认直推）

目标：语义知识库可独立于技能仓演进；**不改** Markdown 内容结构。本地消费一律经 §7.3 的 `kb_root`。

#### 7.8.1 最小改动

| 改什么 | 约定 |
|--------|------|
| 远程仓 | 独立 Git 仓；仓根 = 知识库业务树（README、模块矩阵总览、`{一级}/{二级}/`…） |
| 索引 | **`知识库索引.json` 默认不提交远程**；`.gitignore` 忽略；pull/写入后本地 `rebuild_index` |
| 报告 | 入库报告 / sync 报告 **永不**写入语义仓 |
| 技能仓 | 可保留只读样例；运行时以 `kb_root` 为准 |

**禁止**把整个 `testcase-generation-skills` 仓当成语义库远程仓。

#### 7.8.2 可配置项

`src/config/kb_remote.json`（密钥不落盘；可用环境变量覆盖）：

```json
{
  "enabled": false,
  "repo_url": "https://git.example.com/org/spark-knowledge-base.git",
  "branch": "main",
  "local_path": "E:/data/spark-knowledge-base",
  "auth": { "mode": "https_token", "token_env": "KB_GIT_TOKEN" },
  "pull": { "ff_only": true },
  "push": {
    "mode": "direct",
    "create_commit": true,
    "message_prefix": "kb:",
    "exclude_paths": ["知识库索引.json", "**/*.tmp", ".DS_Store"]
  },
  "conflict_policy": "stop_and_report"
}
```

| 键 | 含义 |
|----|------|
| `repo_url` | 语义库 Git 地址 |
| `branch` | 跟踪并**直推**的分支，默认 `main`（本阶段不强制 PR） |
| `local_path` | 本地检出根 → 即 `kb_root`（enabled 时） |
| `push.mode` | 固定 `direct`：commit 后 `git push origin HEAD:{branch}` |
| `exclude_paths` | 必含索引文件名，防止误提交 |

`enabled=false`：跳过 pull/push，报告 `git_sync=skipped`；仍写默认 `kb_root`。

#### 7.8.3 Pull

```text
kb_git_pull
  1. 校验 repo_url / branch / local_path
  2. 目录不存在 → clone --branch {branch}
     存在但非 git / origin URL 不一致 → 失败退出
  3. fetch；工作区脏且非本次将改文件 → 失败退出（fail-fast，不自动 stash）
  4. merge --ff-only；非快进 → 停止并报告，禁止写盘
  5. rebuild_index（本地）
```

#### 7.8.4 Push 与失败恢复

```text
kb_git_push
  1. fetch；若落后 → 不 push；回传「重新 pull → 复检 diff → 再确认」
  2. stage 业务文件（排除索引与 exclude_paths）
  3. 无变更 → nothing_to_push
  4. commit + push origin HEAD:{branch}
  5. 成功 → 回传 remote commit
```

**push 失败恢复（resume）：**

| 状态 | 行为 |
|------|------|
| 本地已 commit、远程拒绝/网络失败 | 保留本地 commit；报告 `push_pending`；下次入库先 `kb_git_push --resume`，禁止重复堆叠空 commit |
| resume 时发现远程已有新提交 | 停止；指引：`pull --ff-only` 失败则人审合并后再 resume |
| 禁止 | force / force-with-lease；改 tip 历史；删除远程分支 |

#### 7.8.5 并发

| 场景 | 行为 |
|------|------|
| 拉取非快进 | 停止；人审合并后再触发 |
| 确认后、推送前远程超前 | 停止推送；重新 pull → 复检 → 确认 |
| 两台同时直推 | 后推者失败 → resume 流程 |
| 只读生成用例 | 不强制 push；可选启动时后台 pull（P2，默认关） |

#### 7.8.6 新增文件

| 文件 | 职责 |
|------|------|
| `src/config/kb_remote.json.example` | 配置样例 |
| `src/scripts/kb/kb_git_sync.js` | pull / push / status / resume-push |

### 8.1 算法

**挂载点（Fast Path）：** 1A 只提取本次需求；skill 在 **Stage3 模块归属（C-MOD）完成之后、3A 之前** 调用 `extract_kb.js`，让测试点分析结合历史知识。无命中 exit 0，不阻断。

```text
输入：C-CTX、C-MOD、关键字、过滤后正文；kb_root（§7.3）

0. 若本地索引缺失或过期 → rebuild_index（只读生成也允许重建）
1. 读 {kb_root}/知识库索引.json（禁止遍历全库）
2. 模块矩阵总览【机器区】
     → 分层：校验 C-MOD 一级/二级合法
     → 支持矩阵：按 §4.3 计算最终支持；3B 裁标签
     → 【说明区】默认跳过
3. 打开命中模块的 页面关系.md（按端切片）
     → Web 命中页按需提取「前端 URL 模板」为 page_url fact
4. 仅当索引 file!=null 且关键词命中、且页面/元素 status=已确认 时打开页面文件
     → 只取 in_scope 端的命中「核心元素」行（该行所属页须已确认）
     → 同行「后端接口」拆成 backend_api fact；只取命中元素，不取整页接口
     → 只取该行显式引用的补充说明
     → 跳过 frontmatter、页面简介、草稿/待确认页
5. 小程序需求：只走 知识库/小程序/{域}/
6. 数量上限：关系路径≤30；页面 URL≤10；元素≤20；后端接口≤20；补充说明≤8
7. 合并写入 script/stage1/domain_facts.json（source=kb_applied，带 platforms 等）
8. 无命中 / 仅待确认命中 → exit 0，facts 可不增，不阻断生成
```

**状态过滤（P0）：** `草稿` / `待确认` **不得**写入 `domain_facts`；仅供人审与入库 diff。

### 8.3 临时契约扩展（相对 6.1，P0）

`domain_facts.json` 中 `source=kb_applied` 的条目，在 6.1 现有字段上**扩展**（实现时升 schema；`additionalProperties` 仍为 false，须显式加列）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `platforms` | ✓（kb_applied） | 适用端规范枚举子集：`["web"]`、`["app"]` 或 `["web","app"]` |
| `fact_kind` | ✓（kb_applied） | `matrix_note` \| `page_relation` \| `page_url` \| `page_element` \| `backend_api` \| `supplement` |
| `page_id` | 元素/关系建议 | 稳定页面标识 |
| `relation` | 关系类 | `{ "from": "…", "to": "…" }` |
| `element_name` | `page_element/backend_api` | 所属核心元素；接口不得缺失归属 |
| `page_url` | `page_url` | `{ "template": "/path/{id}", "absolute": false }` |
| `backend_api` | `backend_api` | `{ "method": "GET", "path": "/api/v1/x/{id}", "operation": "查询详情" }` |
| `kb_ref` | 建议 | 来源路径或索引 id |

人审临时条（`human_review`）可不填 `platforms`；与 kb 条冲突时 **人审优先**（或显式覆盖），记录于截取/合并报告。

Stage4 **仍禁止**读 `domain_facts.json`（沿用 6.1）。

### 8.4 C-TP / C-TC 技术引用扩展（P0）

为让 URL/API 真正进入用例，同时保持 Stage4 输入隔离，`test_points.schema.json` 与 `test_cases.schema.json` 增加可选 `technical_refs`：

```json
[
  {
    "type": "page_url",
    "platform": "web",
    "page_id": "销售单详情页",
    "target": "/sales/order/{order_id}",
    "kb_ref": "销售/销售/页面关系.md#销售单详情页"
  },
  {
    "type": "backend_api",
    "platform": "app",
    "page_id": "销售单开单页",
    "element_name": "保存按钮",
    "method": "POST",
    "target": "/api/v1/orders",
    "operation": "保存销售单",
    "kb_ref": "销售/销售/子页面_销售单开单页.md#保存按钮"
  }
]
```

契约纪律：

- C-TP：Stage3A 只附加当前测试点实际相关引用；`kb_ref` 必填以支持追溯。  
- C-TC：Stage4 只能从关联 C-TP 复制/裁剪，禁止自行新增 URL/API。  
- XMind：作为独立「技术引用」子节点展示，不混入业务标题；接口验证型用例可同时在步骤/期望引用。  
- `technical_refs` 不改变测试点/用例主键与业务断言；缺失时保持向后兼容。  
- `facts_applied` 报告记录哪些 `DF-*` 转成了哪些 TP technical refs。
